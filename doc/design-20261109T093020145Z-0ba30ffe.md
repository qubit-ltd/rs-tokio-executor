## TE-001：修正重试操作顺序

两种服务的 `capacity_changes()` 均返回 watch receiver。新订阅把已有 generation 视为已读；通知只是重试提示，不预留容量。若收到 Saturated 后才订阅，且容量在拒绝和订阅之间释放，直接等待 changed() 可能在已有空位时一直等下一次事件。

替换中文排障表中“提交被拒绝”这一行的处理方式为：

> 首次提交前订阅容量变化；提交返回 `Saturated` 后等待通知再重试。若收到拒绝后才创建订阅，先立即重试，仍为 `Saturated` 时再等待；遇到 `Shutdown` 则结束重试。

保留现有第101行及两份 capacity_retry 示例中的正确算法。对照英文表格核查语义；其已明确 subscribe before submitting，无需为形式一致改写。无须修改服务内部通知协议，也不新增只匹配这句话的脆弱字符串测试。

验收依据：中文排障表独立阅读时即可确定订阅发生在首次尝试之前，且晚订阅后先尝试而非直接等待；与英文、正文和示例一致。

## TE-002：为结果轮询设置期限

只改 `test_tokio_blocking_task_handle_try_get_reports_pending_then_ready` 中释放任务后的循环。采用 `tokio::time::timeout(Duration::from_secs(5), async { ... })` 包裹原循环，超时诊断为 `released blocking task result remained Pending for 5 seconds`。保留释放前必须 Pending、最终值为7及循环中的 yield_now，继续验证原用例的状态转换。

Tokio time 已在 dev-dependencies 中启用；现有 Duration 已导入，无需增加依赖。5秒是测试等待上限而非执行器性能承诺，避免短计时引入正常调度抖动失败。timeout 能约束此处主动让出的异步循环，不将其描述为能中断任意同步死锁。相邻其他测试不批量改写。

正常路径仍关闭服务。该用例末尾使用已有 `wait_termination_timeout(Duration::from_secs(5))` 并断言，避免结果已发布但服务计数未归零时仍无限等待。这是同一用例有界退出所需的局部配套修改。对于 runtime 析构或同步死锁等更宽边界，依赖现有专门 watchdog 测试，不在本轮引入全套新子进程框架。
